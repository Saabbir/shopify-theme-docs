Cursor, Claude Code, and GitHub Copilot each used to need their own separate rules file, hand-kept in sync. That's no longer necessary — and as of current versions of the Shopify CLI, you don't even have to set it up yourself.

## It's generated automatically, by Shopify's own tooling

Run `shopify theme init` and choose to include AI agent support, and the CLI scaffolds `AGENTS.md` at your repo root — a comprehensive file covering theme architecture, `{% schema %}` best practices, the full Liquid reference (delimiters, operators, filters, objects, tags), translation/localization standards, and worked examples for a snippet, a block, and a section. It also creates `CLAUDE.md` and `.github/copilot-instructions.md` as **symlinks** pointing at that same `AGENTS.md` file — not separate copies, not separate content, the literal same file under two more names.

This means: **Cursor, Claude Code, and Copilot all read the exact same content, always, with zero synchronization step** — because for two of the three, there's nothing to synchronize; they're the same file on disk. Cursor needs no separate file at all — current Cursor versions read `AGENTS.md` natively from the repo root.

## What's actually in Shopify's generated AGENTS.md

It's comprehensive — worth skimming in full at least once, since it covers ground this handbook otherwise repeats piecemeal across several pages:

- **Theme architecture** — the same 8-folder structure and role breakdown as [Folder Structure](/codebase-structure/folder-structure/), with the specific JSON schemas (`schemas/section.json`, `schemas/theme_block.json`, `schemas/theme_settings.json`, `schemas/translations.json`) each file type should validate against.
- **`{% schema %}` good practices** — the single-CSS-property-→-custom-property, multiple-properties-→-CSS-class rule (matches [CSS Style Guide](/style-guides/css/) exactly).
- **The full Liquid reference** — every delimiter, operator, filter (grouped by category: array, cart, collection, color, customer, date, format, hosted file, HTML, localization, math, media, metafield, money, payment, string, tag), every global object (page-specific and cross-template), and every tag, with syntax.
- **Translation and localization standards** — hierarchical `snake_case` keys, sentence case for user-facing text, variable interpolation over string concatenation, the `.schema.json` locale file convention.
- **Worked examples** — a complete snippet (`image`), a complete pair of blocks (`text`, `group`), and a complete section, each with real `{% schema %}` JSON.
- **A mandatory directive**: `🚨 MANDATORY: YOU MUST CALL "learn_shopify_api" ONCE WHEN WORKING WITH LIQUID THEMES.` This tells an MCP-connected AI tool to load current Shopify API context before generating anything — see [Shopify's Official AI Toolkit](/ai-assisted-development/shopify-ai-toolkit/) for what that connects to and why it matters for the "don't guess" discipline this handbook asks for throughout.

Because this file already covers the ground above thoroughly and authoritatively, this handbook's own [Liquid Style Guide](/style-guides/liquid/), [CSS Style Guide](/style-guides/css/), and [Reference](/reference/) pages are written to complement it — day-to-day conventions and worked reasoning — rather than duplicate its exhaustive reference material.

## The one rule for extending it: everything custom goes in "## Custom rules"

Shopify's generated `AGENTS.md` ends with an empty `## Custom rules` heading — a deliberate extension point. **This is the only section you should edit.** Everything above it is Shopify's own generated content, identical to what any Shopify theme project starts from; editing it by hand means your changes could be overwritten or become inconsistent with a future re-scaffold, and it's not project-specific anyway — it's true of every Shopify theme.

Our project's own rules — which base theme we scaffold from, our no-Sass/no-framework constraints, our Figma-to-code workflow, our source-of-truth and no-guessing requirements — all live under `## Custom rules`, at the bottom of the file. [Download our current `## Custom rules` content](/templates/AGENTS.md) to see exactly what Solis adds on top of Shopify's baseline (scroll to the bottom of that file — everything above `## Custom rules` is Shopify's own generated content, reproduced there so the download is drop-in complete).

## Setting it up

**If you're scaffolding a new theme:** run `shopify theme init` and select AI agent support when prompted — `AGENTS.md`, `CLAUDE.md`, and `.github/copilot-instructions.md` (as symlinks) are created for you automatically. Then paste our `## Custom rules` content (from [the template above](/templates/AGENTS.md)) into the `## Custom rules` section Shopify's scaffold already created. **You don't need `scripts/generate-ai-rules.mjs` for this path at all** — the CLI already did what that script does. Don't run it, and don't commit it to the repo unless one of the two scenarios below actually applies to your project.

**If you're adding this to an existing theme repo that wasn't scaffolded with AI agent support** (an older Solis project, or a theme created before AI agent support existed):

1. [Download `AGENTS.md`](/templates/AGENTS.md) — it's a drop-in copy of what `shopify theme init` generates, with our `## Custom rules` section already filled in.
2. Put it at your repo root.
3. [Download `scripts/generate-ai-rules.mjs`](/templates/scripts/generate-ai-rules.mjs) into a `scripts/` folder, and run it once:

```bash
node scripts/generate-ai-rules.mjs
```

This creates `CLAUDE.md` and `.github/copilot-instructions.md` as symlinks to `AGENTS.md` — matching exactly what Shopify's own CLI does. Cursor needs nothing extra; it reads `AGENTS.md` directly.

4. Commit `AGENTS.md` and the two symlinks. Git tracks symlinks natively — commit them as you would any file.

### Do we still need `scripts/generate-ai-rules.mjs` once a theme is scaffolded with AI agent support?

No — for the normal case (a theme scaffolded with `shopify theme init` and AI agent support selected), the script does nothing you need; the CLI already created real symlinks. Running it again is harmless (it's idempotent — see its source) but it's not a step in your regular workflow.

Keep the script in the repo anyway, for two specific situations where it's the only fix:

- **A repo that predates AI agent support**, or was scaffolded without it selected — covered by the walkthrough above.
- **A broken symlink.** Some tools (a "Save As" in certain editors, a zip extract, or a Windows checkout with Git's `core.symlinks` disabled) can silently replace a symlink with a real, static-content file. When that happens, `CLAUDE.md` stops reflecting live edits to `AGENTS.md` — `node scripts/generate-ai-rules.mjs` deletes the stale file and re-links it. If you're on Windows, confirm `git config core.symlinks` is `true` and that Developer Mode (or "Run as Administrator") is enabled for your clone — otherwise Git may check out `CLAUDE.md`/`.github/copilot-instructions.md` as plain text files containing the symlink target path, not real symlinks, in the first place.

If neither applies to your project, there's genuinely nothing to run.

## Updating a rule (the whole workflow)

Because `CLAUDE.md` and `.github/copilot-instructions.md` are symlinks, not generated copies, **there is no regeneration step**. Edit `AGENTS.md`'s `## Custom rules` section, and every tool sees the change immediately — the symlinks always point at the current file content.

1. Edit the `## Custom rules` section of `AGENTS.md` — never the Shopify-generated content above it.
2. Commit. That's it — no build step, no script to re-run, nothing to keep in sync, because there's only ever one real file.
3. Mention the rule change in your PR description, same as any other behavior change — see [Managing & Amending AI Rules](/ai-assisted-development/managing-ai-rules/) for the fuller guideline on how to amend this file well.

| ✅ Do | ❌ Don't |
|---|---|
| Edit only the `## Custom rules` section | Hand-edit Shopify's generated content above it — it'll drift from what a fresh `shopify theme init` produces, and it's not project-specific to begin with |
| Trust the symlinks to stay in sync automatically | Look for a "regenerate" command that doesn't exist anymore — editing `AGENTS.md` is the whole workflow |
| Re-run `scripts/generate-ai-rules.mjs` only if a symlink gets accidentally broken (e.g. `CLAUDE.md` was replaced with a real file by some tool) | Assume a broken symlink will silently fix itself |

## The optional, legacy Cursor `.mdc` approach

Older Cursor versions, or teams who specifically want **per-file-type auto-attach** (a rule that only loads into context when editing a `.liquid` file, say, rather than the full `AGENTS.md` every time), can still use `.cursor/rules/*.mdc` files. This isn't part of Shopify's generated scaffold — it's a hand-maintained addition on top, with a real trade-off: you gain scoped loading, but lose the "one file, always in sync" property, since `.mdc` content has to be manually kept consistent with `AGENTS.md` rather than symlinked to it.

- [`00-project-context.mdc`](/templates/cursor-rules/00-project-context.mdc) — always loaded, project-wide constraints.
- [`01-liquid-and-schema.mdc`](/templates/cursor-rules/01-liquid-and-schema.mdc) — loads when editing `.liquid` files.
- [`02-css-and-js.mdc`](/templates/cursor-rules/02-css-and-js.mdc) — loads when editing CSS/JS.
- [Legacy single-file version](/templates/legacy-cursorrules.txt) for very old Cursor versions without `.mdc` support.

Default to plain `AGENTS.md` (which current Cursor reads natively) unless you have a specific, concrete reason to want scoped auto-attach badly enough to accept the manual-sync trade-off.

## What good rules actually look like

Whether in Shopify's generated content or our `## Custom rules` section, the same standard applies — specific, checkable rules, not vague ones:

| ❌ A vague, low-value rule | ✅ A specific, checkable rule |
|---|---|
| "Write good, clean Liquid code" | "A section either defines blocks locally OR accepts theme blocks via `@theme` — never both" |
| "Follow accessibility best practices" | "Every interactive element must be keyboard operable with a visible `:focus-visible` state" |
| "Use good naming" | "File names: kebab-case. Schema `id`s: snake_case" |

## Testing whether your rules are actually working

A rule that's never been checked against real output is just aspirational documentation. Periodically:

1. Ask your AI tool to build something you know the "wrong" (Dawn-era) pattern for — e.g. a section with inline blocks.
2. Check whether it produces the current pattern (blocks in `/blocks`, `@theme` targeting) or falls back to the old one.
3. If it falls back, the relevant rule in `## Custom rules` needs to be more specific, not just longer.

## Best practices

- Let `shopify theme init` generate the base file whenever starting a new theme — don't hand-write what the CLI already produces correctly.
- Edit only `## Custom rules`. Treat everything above it as Shopify's, not ours.
- Trust the symlinks — there's no regeneration step to remember, which removes an entire class of "forgot to sync" bugs the old three-separate-files approach had.
- Re-test rules periodically against a known "wrong pattern" case, rather than assuming they still work as the tool and codebase evolve.

## Common mistakes

- **Hand-editing Shopify's generated content** instead of confining changes to `## Custom rules` — drifts from what a fresh scaffold produces, for no project-specific benefit.
- **Looking for a "regenerate" step that no longer exists** — editing `AGENTS.md` is the entire workflow now; there's nothing to run afterward.
- **Assuming `.cursor/rules/*.mdc` is still the primary mechanism** — it's optional and legacy now that Cursor reads `AGENTS.md` directly; only add it back for a specific, deliberate reason.
- **Writing rules that are true but not actionable** ("be accessible," "write clean code") — these rarely change actual model output.
